# Audita — Security & Data Protection

Status: v2.0 · 2026-07-27 · applies to the multi-tenant Postgres deployment.
Be honest with prospects: this section says what exists, not what we aspire to.

## 1. Data classification

| Data | Sensitivity | Where |
|---|---|---|
| GSTR-2B, purchase registers, bank statements/ledgers | **High** — client financial data | transient `data/uploads/` tempfiles, parsed into Postgres |
| Recon/BRS reports, invoices (incl. scans), ledgers, workbooks | High — derived financials + reviewer identities | Postgres, every row org-scoped |
| User credentials | **Critical** | Postgres `users` — scrypt hashes only, never plaintext |
| Sessions / invites | High | Postgres — sha256 token hashes only; raw tokens never stored |
| Event log | Medium — operational metadata, actor identities | Postgres `agent_events` (append-only) |
| Signing key | **Critical** | `AUDITA_SECRET_KEY` env (prod) / `data/secret_key` (dev fallback) |

## 2. Current controls

- **Authentication:** email + password (stdlib scrypt, n=2¹⁵, per-hash salt, constant-time
  compare). Opaque 256-bit session tokens in an HttpOnly, SameSite=Lax, Secure cookie;
  only the sha256 of a token is stored, so sessions are individually revocable and a DB
  leak exposes no usable tokens. Sliding renewal past the half-life; logout deletes the row.
- **Tenancy & RBAC:** every workspace (org) is isolated at the query level — all domain
  tables carry `org_id` and every store is constructed per-request with the caller's org.
  Roles per membership: `owner > reviewer > preparer > viewer` (strict hierarchy). Verify
  and sign-off actions require reviewer+; org/member management requires owner. Non-members
  get 404 (org existence is not revealed). Invites are one-shot, role-scoped, 7-day expiring
  tokens (hash-stored) generated by owners.
- **Identity-backed sign-offs:** `verified_by` / `confirmed_by` / CA sign-off come from the
  authenticated session (display name + CA membership no. on the profile), never from a
  typed payload field. The event log records the actor's email on every mutation.
- **Transport:** TLS is the deployment platform's job (Cloud Run / reverse proxy). The app
  must never be exposed on plain HTTP beyond localhost.
- **Report access:** capability URLs — `itsdangerous` signed tokens, per-purpose salts
  (`audita-report-link`, `audita-bankrec-link`), default expiry 7 days
  (`AUDITA_LINK_MAX_AGE`). Tampered ⇒ 404, expired ⇒ 410 (tested). Links are **view-only**:
  verification through a link still requires a logged-in reviewer of the owning org.
- **Upload hygiene:** extension allowlist (`.json .csv .xlsx .xls` / image+PDF for invoice
  scans); app-level size cap (`AUDITA_MAX_UPLOAD_MB`, default 15 MB, 413 beyond); random temp
  names; parsed with stdlib/openpyxl (no macro execution, no pickle).
- **Injection surface:** SQL uses parameterized queries only (psycopg); no shell-outs; Jinja
  autoescaping on server-rendered pages; React escapes by default.
- **Audit trail integrity:** `agent_events` rejects UPDATE/DELETE via Postgres triggers —
  tamper attempts fail at the database, not in app code (tested).
- **Container:** non-root user (uid 1001), slim base image, no build tools in runtime layer.
- **Secrets:** `.env` git-ignored; `.env.example` documents required vars (signing key,
  database URL, optional `GEMINI_API_KEY`).
- **LLM boundary:** Gemini receives invoice *images* for field extraction only when the Vision
  path is explicitly enabled; the ADK agent's tools expose summaries, and the agent cannot
  mutate amounts (tools do the math; instructions forbid recomputation).

## 3. Honest gaps

| Gap | Risk | Required before |
|---|---|---|
| No rate limiting (login, signup, uploads) at app level | Credential stuffing, DoS | Public exposure — set platform limits (Cloud Armor / proxy) meanwhile |
| Open signup — anyone can create a *new empty* workspace | Spam workspaces (no data exposure: strict org isolation) | Fine for pilot; add email verification or an allowlist before broad marketing |
| No password reset / email verification flow | Locked-out users need operator help; unverified emails | First external pilots |
| No encryption at rest at app level | DB access = data access | Rely on Cloud SQL disk encryption (GCP default) now; app-level envelope encryption later |
| Upload tempfiles retained until restart/purge | Data minimization over time | Scheduled purge (uploads > 30 days) before non-founder-network clients |
| No session listing / remote revocation UI | A stolen session can't be self-served away (operator can delete the DB row) | Multi-user pilots at scale |

## 4. DPDP Act posture (India)

Pilot commitments (must be kept, they're in the product's marketing):
1. **Consent:** written consent from each pilot business before processing; purpose limited to
   producing their report.
2. **Deletion on request:** delete `data/uploads/*`, the client's reports, and derived JSON on
   request. (Event-log rows are metadata, retain for integrity; they contain no financial
   figures from client docs beyond aggregate refs.)
3. **Residency:** deploy in **GCP asia-south1 (Mumbai)**; Gemini calls use Google's API —
   disclose this in the consent note when Vision is enabled.
4. **Breach duty:** DPDP requires notifying the Data Protection Board and affected principals;
   maintain the incident checklist below.
5. Full DPDP design (retention schedules, consent management, DPO designation as applicable)
   is scheduled with the CA-review layer phase — before scaling past founder-network pilots.

## 5. Threat model (abridged)

| Threat | Vector | Control |
|---|---|---|
| Report link leaks | forwarded email/chat | expiry + regeneration; links are view-only — verification requires an authenticated reviewer |
| Stolen session cookie | XSS elsewhere / device theft | HttpOnly+Secure+SameSite; DB-backed revocable sessions; 30-day expiry |
| Cross-tenant access | crafted org_id in URL | membership check on every request; 404 for non-members (tested) |
| Malicious upload | crafted xlsx/json/csv | allowlist, safe parsers, size limits at proxy, container isolation |
| Trail tampering | insider/compromise edits history | DB-level append-only triggers; future: hash-chain + periodic external anchor |
| Signing key theft | env/dev file leak | prod key only via secret manager; rotate ⇒ all links invalidate (feature, not bug) |
| Prompt injection via invoice images | adversarial text in scans | Vision output is structured fields feeding deterministic code; no tool-calling from vision output |
| Wrong ₹ headline | engine bug / LLM drift | LLM never computes; ambiguous ⇒ unresolved; human verification gate; 62 automated tests |

## 6. Incident checklist

1. Revoke: rotate `AUDITA_SECRET_KEY` (kills all live links), redeploy.
2. Freeze: snapshot the `/data` volume (evidence, incl. append-only log).
3. Assess scope from `agent_events` (what ran, when, by whom).
4. Notify affected pilot businesses; DPDP Board notification if personal data involved.
5. Post-mortem in `docs/incidents/`.
